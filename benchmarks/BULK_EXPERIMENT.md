# 补测：256请求批量吞吐

之前的实验回答的是：请求陆续到达时，长输入会不会打断正在输出的答案。这一组换个问题：**把256个请求一次交给引擎，总共生成这些答案需要多久？**

用Qwen3-0.6B，是为了对齐nano-vLLM官方展示的模型规模和负载。它不能与之前Qwen3-8B的在线吞吐直接比较，也不能仅凭数字比师兄的Qwen2.5-0.5B快或慢，就判断代码优劣。

## 固定什么，比较什么

负载生成顺序对应上游的[bench.py](https://github.com/GeeeekExplorer/nano-vllm/blob/main/bench.py)：先生成全部输入及其中的随机token，再生成输出长度。默认seed为0。

| 项目 | 默认值 |
|---|---|
| 模型 | 本地Qwen3-0.6B，使用模型配置的dtype |
| 请求数 | 256，一次性入队；不是保证256条同时执行 |
| 输入、输出长度 | 分别随机100～1024 token |
| 输入token ID | 随机0～10000，与官方脚本相同 |
| 总输入 / 总输出 | 142,827 / 133,966 token |
| 最长输入加输出 | 2,011 token |
| 请求数上限 / 每步token预算 | 512 / 16,384 |
| 最大上下文 / 显存利用率参数 | 4096 / 0.9 |
| 调度对照 | 当前代码的prefill_first与mixed |
| KV分配 | 均为full；自动池容量必须相同才生成比较结果 |
| 执行方式 | 纯decode保留CUDA Graph，mixed混合轮次走eager |
| 采样 | temperature=0.6，ignore_eos=True，逐请求校验输出长度 |

这不是未修改上游nano-vLLM与vLLM的对比。mixed还会跳过未完成prefill的无效LM head/采样，收益不能全归因于调度顺序。

官方脚本先做一个短请求预热，再计时一轮。这里为了观察波动，每种策略用完整负载预热2轮、测量3轮；每轮清空前缀缓存元数据，保留模型、GPU KV张量和编译结果。计时前后同步GPU，使用perf_counter。因此是**官方同款负载的补测，不是逐项完全相同的官方协议复现**。

## 怎么运行

先把新增脚本同步到云端，在原nano-vllm虚拟环境中运行；不要用另建的vllm-study环境。下面模型路径只是示例，需要先有完整的Qwen3-0.6B权重；已有的Qwen3-8B不能代替这一组。

```bash
cd /root/shared-nvme/nano-vllm-lab
source .venv/bin/activate
MODEL=/root/shared-nvme/models/Qwen3-0.6B

# 不加载模型、不使用GPU、不写文件，先检查负载和参数
python bench_bulk.py --model "$MODEL" --dry-run

# 正式测试：两个独立进程依次执行，避免同时争抢GPU
python -u bench_bulk.py --model "$MODEL"
```

默认共10轮完整负载，另有两次引擎初始化；比官方只计时一次的脚本耗时更长。每个子进程默认超时30分钟，可通过`--timeout-s`修改。运行时会打印结果目录与日志位置，另开终端用`tail -f 日志路径`看逐轮进度。

如果只想先检查能否跑通，可以加`--warmup 1 --repeats 1`。这一趟不是默认三轮正式结果。

若两种策略的自动KV池容量不同，脚本会保留各自结果但拒绝计算对比。查看两份metadata.json的kv_pool，选择不超过两者的块数，通过`--kv-cache-blocks N`重新运行两种策略，并把它记录为固定池配置；不要把不同池容量的两次结果拼起来。

## 看哪些文件

默认写入新的`results/bulk-时间-随机后缀/`，不会覆盖旧目录。

- `comparison.json`：两种策略的吞吐统计，以及mixed相对prefill_first的变化。
- 根目录`metadata.json`：运行状态、子进程命令和退出码。
- 每种策略目录下的`metadata.json`：环境、代码版本、模型元数据哈希、权重大小、实际KV池。没有完整权重哈希，因此要保留同一份模型快照。
- `rounds.csv`：逐轮耗时、实际输出量、吞吐、抢占次数和重算token量。
- `workload.json`与各轮`*-outputs.json`：实际输入、长度要求和生成token。
- 根目录两份日志：运行进度和失败原因。失败时不要只发最后一行报错。

吞吐计算为：

```text
每轮实际输出token数 ÷ 本轮generate耗时
```

计时包含入队、调度、模型运行、CPU结果回传及最终文本解码，不含初始化、缓存重置、结果校验和文件写入。输出量不是把输入也算进去；不保证每条请求的生成速率都达到总吞吐。

先看每轮输出是否都是133,966，再看三轮吞吐波动、抢占和重算情况。**这组不测TTFT/ITL，不代表在线服务能力或已经找到硬件最大吞吐，也不预设mixed一定更快。** 结果拿到后再补入报告，目前没有GPU实测数据。
