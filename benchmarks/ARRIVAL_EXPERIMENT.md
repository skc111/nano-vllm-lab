# 持续到达实验：三种调度策略，同一KV配置

## 这次回答什么

之前两个请求的实验说明混合调度可以减轻一次长prompt造成的停顿。
这次检查：**请求连续进入时，该效果能否保留？是否只是把等待转移给新请求？纯短请求会不会退化？**

本次不改引擎，不重新安装环境，也不重复已有GPU正确性诊断。
它是有限长度、周期到达的探索实验，不是完整服务压测或已证明的稳态容量测试。

## 运行

在已验收的云端4090环境，拉取本分支后进入仓库并激活原虚拟环境：

```bash
cd /root/shared-nvme/nano-vllm-lab
source .venv/bin/activate

# 只看计划，不加载模型、不启动GPU子进程，也不创建结果目录
python run_arrival_experiment.py --plan-only

# 正式执行；无需在云端再跑一次CPU测试
python -u run_arrival_experiment.py \
  --model /root/shared-nvme/models/Qwen3-8B
```

**默认仅等待请求到达就至少需要15.5分钟。** 这不是总耗时估计，还需加12次引擎初始化、编译、
所有请求完成前的收尾时间及文件写入。不要把它当成两分钟测试；终端连接需保持。

如只想先验收入口，可运行较小的试跑，但不能拿它代替默认矩阵或尾延迟结论：

```bash
python -u run_arrival_experiment.py \
  --model /root/shared-nvme/models/Qwen3-8B --requests 8 --rates 4
```

任一子任务失败便停止并保留日志，不丢弃失败请求后继续报“成功”。先分析失败原因，不盲目重跑整套。
默认输出目录为`results/arrivals-时间戳/`；自定义`--output-dir`必须是不存在的新目录。

## 默认矩阵

| 负载 | 每轮请求 | 到达方式 | 对比策略 |
|---|---|---|---|
| 长短混合 | 24短 + 8长，每4个请求中的第4个为长请求 | 等间隔1、2、4请求/秒，分别测试 | prefill_first / interleave / mixed |
| 全短负对照 | 32短 | 等间隔4请求/秒 | 同上 |

- 短请求：128输入、64输出；长请求：4096输入、32输出。随机非特殊token用于控制形状，不代表自然语言质量。
- 固定`ignore_eos=True`、temperature=0.6、seed=0；同一负载各策略的输入token与计划到达时间相同。
- 每配置2轮完整预热、3轮测量；每轮重置前缀缓存元数据，但保留模型、KV tensor和编译缓存。
- 单卡BF16，`max_num_seqs=8`、每轮512计算token、`max_model_len=4352`。
- **全部使用`kv_allocation=full`、64个256-token物理块**，不把按需分配混进本次比较。
- 全部`execution=graph`：保留正常纯decode Graph；mixed的混合forward仍走eager路径。
- 策略执行顺序在不同负载之间轮换，但同一配置的重复在一个进程内完成，不等于严格随机交错A/B。

1/2/4请求每秒只是探测点，不预设哪个点已经饱和。64块是固定资源的机制对照，**不是4090极限容量**。
高负载下可能出现KV限制，因此同时记录占用、等待队列、抢占与重算。
mixed还跳过partial prefill的无效logits/采样，其收益不能全部归为调度顺序变化。

## 自动输出及指标解释

- `comparison.csv`：每个负载/策略/请求类型一行，便于发回分析。
- `comparison.json`：每轮指标，以及跨轮中位数/最小值/最大值和警告日志摘录。
- `mixed-arrival-curves.svg`：吞吐、短请求TTFT p95、短请求最大ITL的p95曲线。
- `suite.json`、各任务完整日志、各轮`timeline.json`/CSV、模型与环境元信息、输入trace和脚本副本。

统计口径：

1. **吞吐**＝这一轮全部真实输出token / 包含到达间隔及收尾的墙钟时间。
   低到达率下，它可能主要由请求到达速度决定，不能直接当GPU速度。
2. **计划TTFT**从计划到达算起，包含回放器因当前step未结束而延迟入队的时间；同时报告实际入队TTFT和入队延迟。
   token在`step()`返回时被观察，没有网络/HTTP延迟，不是客户端指标。
3. **token ITL p95**对所有相邻输出间隔取分位数；输出长的请求贡献更多样本。
   **request-max ITL p95**先取每条请求最坏的一次间隔，再对请求取分位数，防止少数长停顿被大量正常间隔淹没。
4. 分位数使用排序后`(n-1)*q`位置的线性插值：**每轮先算，再跨轮汇总**，不会把同一trace重复三次冒充三倍独立请求。
   每轮混合负载只有24短/8长，p95只是样本描述，尤其长请求子集很小，不报p99保证。
5. **积压**从计划到达至末token计算，包含尚未实际入队的到达请求；另报实际入队后的在途峰值。
   最后一次到达时的未完成数、收尾时间用于观察积压，不能单凭有限trace断言队列长期稳定。
6. 预热不保证覆盖所有到达相关shape。保留编译警告和逐轮波动；曲线误差条是跨轮min/max，不是置信区间。

两策略的资源或版本不一致、输出token不完整、汇总与原始时间线不一致时，分析工具会拒绝汇总。
已有GPU诊断不代表本次所有新batch shape都获得完整数值验证；若出现执行错误或异常输出，应停止排查。

## 跑完之后

先看三件事：短请求停顿是否改善、长请求首token是否付出代价、积压/KV压力是否改变。
全短请求则作为新增调度逻辑的负对照。无收益或退化照样保留，不自动追加更多机制或无边界扫参。

把`comparison.csv`和`suite.json`发回，完整结果目录打包留存；释放云实例前确认备份可读取。
不用GPU也可以重新生成汇总和图：

```bash
python -m benchmarks.arrival_metrics results/arrivals-时间戳
```

该命令只读原始JSON/日志并写分析结果，不执行结果包里的脚本。后续如需扩大样本，可调整
`--requests`（至少8且为4的倍数）和`--rates`，同时给`--timeout-s`留足最后到达及收尾时间；先用`--plan-only`核算时间。
